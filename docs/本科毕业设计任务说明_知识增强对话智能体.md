# 本科毕业设计任务说明

## 面向工程设计文档生成的知识增强对话智能体设计与实现

编制日期 2026-10-30　｜　建议周期 12 周　｜　一名学生独立完成

## 1 课题背景与目标

工程设计初期，用户往往只能给出不完整的意图，技术资料分散，讨论中的条件也会反复修改。本课题要求基于 Pi 构建一个独立的对话智能体，通过多轮澄清、知识检索和方案讨论，逐步形成由用户确认、有资料依据、可以继续修改的方案级设计文档。

请选定一种范围明确的通用工程设计场景，例如小型环境监测设备的总体方案设计。该示例仅供选择，具体场景、资料与评价清单在前两周与导师确认。目标是辅助形成总体设计方案，不包含 CAD 建模、复杂工程仿真或专业认证。

### 独立开发方式

在独立仓库自行设计数据结构、接口、前后端和实验，使用公开资料或可复查的受控样例。只需了解通用项目背景，无需读取或修改已有项目，不依赖其数据库、接口、运行服务或私有数据。后续由维护者参考本课题的代码、方法和实验，自行决定如何改造其他项目；兼容、集成和即插即用不属于学生任务。

### Pi 的使用定位

本课题所指 Pi 为 Mario Zechner 发起的开源 Agent 项目，当前官方仓库为 earendil-works/pi。建议使用 Pi SDK 与扩展机制复用 Agent 运行、工具调用、会话和事件能力，先完成应用扩展；只有明确需要时才修改 Pi 核心。[1][2]

学生的主要改进是结构化上下文管理和知识驱动的澄清决策，并将其用于设计文档的持续形成。Pi 既有能力、第三方库与本人新增实现应在论文和代码中分别说明；采用的 Pi 版本或提交、模型、提示词与依赖版本需要固定记录。

### 完成时应具备的闭环

用户表达设计意图 → 更新需求与方案状态 → 选择检索或追问 → 组织知识证据 → 确认设计要点 → 生成文档草稿 → 根据修改更新相关章节 → 用户确认并导出。

## 2 功能需求与交互要求

### 必须完成的功能

| 编号 | 功能 | 可观察的完成标准 |
|---|---|---|
| F1 | 会话与需求澄清 | 能新建、保存和恢复会话；支持补充、修改、跳过问题和结束讨论 |
| F2 | 独立知识库 | 支持 Markdown/TXT 资料导入、分块、检索与来源查看；记录资料名称和片段编号 |
| F3 | 对话行动选择 | 根据意图、缺失项和证据，选择回答、追问、提出候选、确认冲突或总结 |
| F4 | 状态与历史 | 保存有效需求、待确认项、冲突、方案选择及修改记录；重新打开会话可恢复 |
| F5 | 证据与确认 | 回答和设计建议可查看依据；区分用户确认、知识事实、系统建议与假设 |
| F6 | 设计文档 | 按固定章节生成、预览和更新；支持针对章节修改并保留旧版本 |
| F7 | 检查与导出 | 提示遗漏、冲突、无依据声明和待确认项；支持 Markdown 与 Word 导出 |

功能可以分期实现，但最终演示必须走完“对话到设计文档”的完整路径。模型、检索或导出失败需明确提示，保留已确认内容，并允许重试；未实现的能力不能用固定成功结果代替。

### 知识库与对话协同

用户问概念时，可检索后回答；缺少影响选型的使用条件时，优先追问；资料给出多种候选时，解释差异并让用户选择；资料不足或相互冲突时，展示不足与冲突，保留未知。知识片段中的指令不改变系统角色或工具权限，生成结论要核对来源与适用条件。

知识库中的推荐值不自动成为用户要求。设计中使用的数值应来自用户明确输入、适用资料或可复查的确定性计算；单位和来源一并保留，依据不足时列为待确认。资料适用性不能仅凭向量相似度认定。

### 前端界面

以聊天区和设计文档预览为主体，配套需求状态与证据面板。用户应能查看本轮追问目的、编辑需求卡片、查看引用原文、确认候选方案，以及针对文档章节提出修改。用明确状态提示“已确认、待确认、冲突、草稿”，避免把建议显示成既定结论。

## 3 研究重点与建议技术路线

### 研究重点一 结构化上下文管理

在 Pi 会话和历史压缩基础上，单独维护需求、方案与证据状态，组织为“最近对话、当前有效事实、相关知识片段、必要历史摘要”。Pi 已提供压缩与扩展入口；本课题要设计面向设计任务的组织规则，并验证效果。[2][3]

至少保留需求项编号、内容或取值、单位、状态、来源轮次或证据、被替代关系，以及与文档章节的关联。明确修改后更新有效值并记录旧值；含义不清的冲突先询问；话题切换后仍应恢复此前有效结论。数值、否定条件和修改记录采用结构化保存，不仅依靠自由文本摘要。

研究问题是：与默认上下文策略相比，结构化管理能否提高关键事实保持率和修改生效率，减少重复追问，并控制输入 token 开销？

### 研究重点二 知识驱动的澄清决策

建立可解释的行动选择策略。可从“冲突优先、关键缺失优先、影响多个后续选择的条件优先”起步，结合证据是否适用、是否足够决定回答或追问；设置重复问题抑制、单轮问题数量和总轮次上限。

研究问题是：相较于普通提示词或固定清单，结合需求状态与知识证据选择追问，能否在同等交互预算下形成更完整、矛盾更少、依据更清楚的设计文档？查询重写、引用和成稿是支撑功能，不必分别扩展成独立研究课题。

### 建议实现方式

建议采用 TypeScript 和 Node.js 承载 Pi SDK，React 实现浏览器前端，SQLite 保存会话、状态、文档版本及资料元数据。检索可用轻量本地向量索引或熟悉的检索库，embedding 与语言模型通过可配置接口调用。具体包和接口以选定 Pi 版本的官方文档为准。[1][2]

业务工具可划分为检索知识、读取证据、查询或更新需求状态、生成或修订文档。工具名称与数据格式自行设计，结构校验、状态更新和执行次数由程序控制。需求与章节的关联先用显式规则建立，复杂语义影响分析可作为扩展。

建议采用单 Agent 和有限行动集合，限制为一种设计场景、一套模板。复杂多 Agent、模型训练、图谱平台、语音、多模态与生产权限系统均不列为必交内容。

## 4 最终设计文档的内容与质量

系统生成的是用户所讨论对象的方案级设计文档，与介绍本软件实现的毕业论文相区分。文档应随对话逐步形成，核心章节和关键结论经过用户核对，最终可导出编辑。

| 章节 | 必须体现的内容 |
|---|---|
| 1 设计背景与目标 | 应用场景、问题、设计目标与范围 |
| 2 需求与约束 | 已确认功能、性能、环境和限制；重要条件的来源 |
| 3 总体设计方案 | 系统组成、模块职责、关系及必要方案说明 |
| 4 关键模块设计 | 模块输入输出、工作方式和与其他模块的联系 |
| 5 技术路线与选型依据 | 候选方案、选择理由、适用条件与参考证据 |
| 6 工作流程与接口 | 主要流程、模块间信息或物理接口的方案说明 |
| 7 关键参数与验证方案 | 参数、单位、来源或计算依据；拟采用的验证方法 |
| 8 待确认事项与参考资料 | 假设、缺失证据、未决问题、引用清单 |

### 修改与一致性要求

文档生成应绑定一份明确的需求与方案状态。用户修改条件后，提示可能受影响的章节，更新相应内容，保留原版本及修改说明；修改前已获确认的内容若被改变，需要重新提示确认。首版可用需求项与章节的显式关联实现，不要求自动理解任意文档。

例如，用户把设备使用环境由室内改为室外，系统应更新当前需求，检索适用环境条件，追问尚未确认的信息，并修改涉及环境、防护和验证方法的章节。资料未给出适用防护等级时，不自行编造一个值写入方案。确认过的室内限定不应继续作为当前要求出现在其他章节。

### 导出与检查要求

Markdown 和 Word 应来自同一版本的数据，具有可读标题、参数表、引用和待确认清单；记录文档版本及生成时间。导出前检查必需章节、关键需求覆盖、已知数值或状态冲突、无依据声明和待确认项。检查只能说明已实现规则的结果，不代表自动证明全部工程结论正确。

材料不足时仍可生成明确标识的草稿，缺口集中列出；不可把未决内容写成用户已确认结论。验证方案写计划，不把未执行的试验写成完成结果。

## 5 数据准备与实验设计

### 数据与场景

选择可公开取得、适用范围清楚的技术资料，建立一个规模适中的独立知识库，保留出处、版本和片段编号。需求场景应覆盖初始信息不完整、指代省略、数值修改、前后冲突、证据缺失和方案切换。调试集与测试集按完整场景分组，同一场景的改写或轮次不分散到两边。

先用约 10 个完整对话场景做先导验证，再按预算与导师确定正式数量。此数量仅为起步建议，不代表统计充分性。每个场景预先标注关键需求、可用证据、修改事件、预期确认点和文档检查清单；构造与真实整理案例分开说明。

### 对比与消融

| 实验组 | 保持共同条件后的区别 | 目的 |
|---|---|---|
| G0 基线 | Pi 加相同检索工具与模板，普通澄清提示词，默认上下文策略 | 建立可运行对照 |
| G1 上下文改进 | 在 G0 上增加结构化状态与上下文组织，保持行动提示规则相同 | 检验上下文机制 |
| G2 决策改进 | 在 G1 上增加缺口与证据驱动的行动选择 | 检验澄清决策的增量 |

固定模型、知识库、文档模板、交互/工具预算与评价场景；记录各组提示词、压缩配置和缓存策略。短对话未触发默认压缩时，不声称比较了压缩效果；需另设可控长对话/输入预算条件。模型有随机性时安排可承受的重复运行，保留逐场景结果，不只报平均分。

### 评价指标

文档核心指标包括关键需求覆盖率、需求到文档一致性、证据支持率、修改更新正确率与跨章节矛盾数。明确分母：已确认关键需求、可判定的引用声明、已标注受影响内容等，不能仅用字数或章节齐全代替设计质量。

对话指标包括有效追问比例、重复问题率、关键事实保持率、澄清轮次、token 和耗时。先制定人工标注量表；模型评分只作辅助，真实用户试用与脚本/模型模拟用户分开报告。指标未提升时分析检索、状态、决策或生成环节的原因，避免更换测试集追求正结果。

## 6 进度安排与验收

| 周次 | 阶段成果 |
|---|---|
| 1 至 2 | 学习 Pi SDK，确认场景、资料、模板、指标与预算；跑通工具调用和一个对话，提交 UI 草图 |
| 3 至 4 | 完成知识导入/检索、会话保存和最小前端；跑通 G0 与首份设计文档草稿 |
| 5 至 6 | 完成结构化需求/方案状态、上下文组织和 G1；验证修改与冲突场景 |
| 7 至 8 | 完成澄清决策 G2、章节关联、版本修订与两种导出；通过小规模闭环演示 |
| 9 至 10 | 冻结数据/配置，做正式对比和消融，整理失败案例与文档人工评价 |
| 11 至 12 | 完成论文、代码/数据/运行说明、最终实验记录及答辩演示 |

### 交付清单

交付独立源代码仓库、前后端运行与依赖说明、Pi 版本及使用范围说明、资料来源与场景标注、需求/状态与模板设计、实验脚本和原始结果、毕业论文及演示材料。另提供由原型实际生成的一份完整设计文档，以及一次条件修改前后的文档版本和证据记录。

源码应清楚划分 Pi/第三方能力和本人新增模块，保留来源及许可信息。语言模型、embedding 和其他付费服务的可用性与预算在第 2 周前确认。模型故障时可回放已保存结果展示交互，但必须标明回放，不能冒充实时生成。

### 最终演示路径

从不完整设计意图开始，展示知识检索、主动追问与状态更新；中途修改一项重要条件，展示冲突/变更处理；确认方案并生成设计文档，查看引用与未决事项；针对一个章节提出修改，展示受影响内容更新，最后导出 Markdown 和 Word。关闭重开会话后能恢复已保存结果。

验收以独立系统、完整闭环、两项改进及可复查实验为准。若进度受限，先减少资料格式、场景数或高级界面，保留知识检索、状态管理、决策对比和设计文档输出。复杂工程计算、生产集成或特定领域认证不作为验收内容，最终按学校与导师要求执行。
