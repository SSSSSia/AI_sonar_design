## 3. 归因与观察（A-16 如实）

1. **A2 是最大头（51%）**：两次 LLM 调用（方案文档组织 + 参数四件套），公网 DeepSeek 单次 100–150s 属供应商侧延迟，平台无放大效应（mock 对照同阶段 0.5s）。
2. **检索不是瓶颈**：现部署 graphrag SDK 未装，检索走自建 Neo4j 图谱级/Milvus 向量级，P95 1.3s；A1 的 4~8 条子查询批检索总耗时秒级。**T10.4 检索查询优化不触发**（判定依据 §5）。
3. **CSR 抽验**：4 轮 ir4.csr = 100 / 100 / 100 / 80——round-4 的 80 分是 LLM 真实生成了越界参数被 T9.3 军标核对捕获（CHK-STD-VIOLATION），验证 CSR 口径端到端有效，非基线异常。
4. **旧基线作废声明**：参考文档《系统实施方案》§6.2 的「597.4s 三阶段 demo」为旧原型数据，与本基线无可比性（架构/供应商/口径均不同）；GAP-001 §5 偏差表已更新引用本报告。

## 5. T10.4 条件触发判定

- **判定口径**（任务书 §2.4）：基线检索阶段 > 4 分钟才启动优化。
- **实测**：检索 P95 1.3s（Prometheus `histogram_quantile(0.95, sum(rate(py_kb_query_duration_seconds_bucket[30m])) by (le))`，容器栈实测值）；A1 全阶段（含批检索+LLM）中位 36.5s。
- **判定**：**未触发**（1.3s ≪ 240s 阈值，余量 >180 倍）。A1 子查询归并（8→3）、Neo4j 批量查询等候选措施不在本期实施，留待检索规模增长后复评。
