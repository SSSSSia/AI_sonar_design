## 补充 3 · T13.3 语义脱敏的两次返修（占位符设计教训）

- **嵌套占位**：占位符 `[SENS-1]` 内的 `SENS-1` 恰好匹配「≥2 字母-数字」编号规则 → 被二次捕获成 `[[SENS-4]]`。修复：占位符改 `[SENS_n]`（下划线不匹配任何规则）+ 身份扫描先行、显式注册后行。
- **标签词吞噬**：`(?i)(型号|代号)...\s*` 形态 sub 会把「型号：」标签词一起替换 → restore 后原文缺损。修复：`m.group(0).replace(m.group(1), placeholder)`——只替换捕获组、保留标签词，restore 后原文完整。
- **数值不脱敏的决策**：A2/A3/A4 数值推导/建模/校验依赖真实值参与 LLM 侧算术，占位符无法计算，盲脱破坏工程正确性——机制通道保留（numeric_items + SANITIZE_SEMANTIC_NUMERIC），默认关并如实标注（A-16）。§9.3 数值剥离的完整落地依赖「占位化 + 确定性 solver 代入」架构改造，属生产化纵深项。

## 补充 4 · T13.5 实机返修：网关默认 TimeLimiter=1s 掐断慢端点（本阶段最有价值发现）

- 症状链：py 直连 export/pdf 200（98KB PDF）→ 经网关 503（恰好 1.01s）→ Prometheus 熔断器状态 closed → 排除熔断 → **Spring Cloud Gateway CircuitBreaker 过滤器默认 TimeLimiter=1s**，8s 级 PDF 转换被超时进 fallback（复用熔断降级文案，误报「熔断保护中」）。
- yaml 方式（`resilience4j.timelimiter.instances`）在该 starter 装配下**不生效**（实测仍 1.0s）——`spring-cloud-starter-circuitbreaker-reactor-resilience4j` 的工厂默认配置不经 yaml autoconfig。修复：编程式 `Customizer<Resilience4JCircuitBreakerFactory>`（`config.ResilienceCustomizerConfig`），pyEngine 路由 TimeLimiter 120s + 熔断参数显式声明（对齐 T9.4 口径）。
- 教训：**同步长操作过网关必配 TimeLimiter**；既有 docx 导出（<1s）从未触发此雷。副作用观察：早前单测触发的熔断打开窗口会误伤正常请求（半开 30s 恢复）。
- 另：宿主端口 3000 与前端冲突，gotenberg 映射改 3010（栈内仍 3000）。
