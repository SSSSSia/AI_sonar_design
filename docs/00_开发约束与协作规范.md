## 2. 架构与技术选型（完整版，全量实现）

v2 按 P2《智能辅助声呐装备设计系统_总体设计方案》的**完整五层架构全量实现**，不做 demo 级裁剪：Java+Python 双后端、网关鉴权、五步主线 Agent、完整数据底座（PG/Neo4j/Milvus/MinIO/Redis）、知识库文档预处理管线、审阅关与溯源全部落地。

仅以下两类内容除外（且必须如实标注）：
1. 设计文档中明确标注**远期/后续扩展**的项（见 2.1 暂缓清单）；
2. 依赖专用硬件的**部署形态**（昇腾 910C + vLLM 私有化、军网内网）——开发期以公网 OpenAI 兼容 API 作为 LLM 适配器的 fallback（P2 §4.7 允许），接口与配置按私有化部署预留。

**暂缓（仅限设计文档明确标注的远期/后续扩展项）**：多声呐类型规模化泛化、修复策略自学习、多方案比选、三维视图点击反向定位（交互式精化）、多租户、实际军网/昇腾部署。
暂缓项若要提前动工，必须先补设计文档并走 ADR。

## 3. 架构硬约束（不可违背项）

以下约束来源于 P1 定稿与 P2 设计底本（源头为已归档的历史代际文档，见 ADR-006），违反任何一条即为架构走偏，必须回退：

| 编号 | 硬约束 | 说明 |
|---|---|---|
| A-01 | **固定管线，禁止自由协商** | A1→A2→A3→A4→A5 顺序由编排层写死，**禁止 LLM 自主决定"下一步调用谁"** |
| A-02 | **一能力一 Agent** | C1–C5 对应 A1–A5，不合并、不拆散；新增能力优先评估为横切服务 |
| A-03 | **Agent 不互调** | Agent 之间只通过 IR 经编排层传递，禁止直接 import 彼此的执行入口 |
| A-04 | **IR Schema 单一事实源** | IR0–IR5 的字段定义只在一处维护（根目录 `contracts/ir/`，JSON Schema 为准，Java/Python 两侧代码由 schema 生成或校验对齐）；改契约 = 改一处 + 全链路回归 |
| A-05 | **编排层只做三件事** | 按序调用 Agent 传 IR；审阅关暂停/裁决/局部回环；维护 IR 版本。编排层不做业务决策、不写业务逻辑 |
| A-06 | **参数来源四分类强制** | 每个参数必须有 `source_type ∈ {formula, case, standard, estimated}` + `source_ref` + `derivation` + `trace_id`；缺来源的参数不允许进入 IR2 |
| A-07 | **LLM 介入白名单** | LLM 仅允许用于：需求理解与子查询规划（A1）、文档组织（A2）、代码组装与修复（A3）、沉淀候选整理（A5）。**公式类参数取值必须由代码计算**（SymPy 等），不得由 LLM 给出数值 |
| A-08 | **A3 不改参数** | CAD 建模严格继承 IR2 参数；发现矛盾抛回 A2，不自行调数 |
| A-09 | **A4 只出报告** | 校验发现问题生成结构化 IR4，不直接改参数 |
| A-10 | **A5 回写需人工确认** | 知识沉淀以 `pending` 候选产出，经知识审阅关确认后才写入图谱 |
| A-11 | **两道审阅关必须落地** | 审阅关①（IR2 后）、审阅关②（IR3 后），不通过走**局部回算**，禁止整链路重跑 |
| A-12 | **局部重算依赖 IR 版本** | 每个 IR 追加不可变快照；回退只重跑受影响 Agent，下游产物按需失效 |
| A-13 | **有界终止** | 一切重试/修复循环必须有可配置次数上限；超限必须降级输出并如实说明，禁止死循环或静默失败 |
| A-14 | **检索三级降级** | 图谱检索（local）→ 向量检索（basic）→ 文本关键词，任一级失败降级不报错中断 |
| A-15 | **计算密集逻辑在底座** | 约束求解、CAD 执行在独立底座模块，Agent 只做理解、组织、裁决 |
| A-16 | **诚实交代原则** | 军标 0 条就标"待补"；知识缺口如实进 `missing_items`/`gap` 清单；禁止在 UI 或报告中夸大能力 |

### 3.1 模块职责边界表（实现对照基准）

实现时以 P1《系统总体架构定稿》§4 的服务与 Agent 职责边界表为准（源头：已归档核心版 §2.3 与项目总体设计 §4.2），每个 Agent 代码文件的 docstring 中必须引用对应边界描述。核心速记：

| 模块 | 做什么 | 不做什么 |
|---|---|---|
| A1 需求解析 | 拆解需求、规划 4~8 条子查询、并行检索 | 不推导几何参数、不赋值 |
| A2 方案生成 | 产出设计文档 + 带出处的参数表（**IR2 是全系统枢纽**） | 不解复杂隐式方程、不写 CAD 代码 |
| A3 CAD 建模 | 范例匹配 → 生成 CadQuery 脚本 → 静态校验 → 执行出 STEP | 不改参数数值 |
| A4 合规校验 | 按 source_type 分流校验 + 几何自洽 + 军标核对 | 不改参数 |
| A5 知识沉淀 | 筛选、去重、产出回写候选 | 不写未经验证的决策 |

## 5. 前后端接口契约约束

1. **契约先行**：先写 `docs/api/openapi.yaml`（或由 FastAPI 生成后固化导出），前端据契约开发/联调；契约变更单独提交，提交信息标 `api:`。
2. **版本化路径**：全部接口挂 `/api/v1/...`，破坏性变更升 `/v2`，不原地破坏。
3. **统一响应包**：`{ code, message, data, trace_id }`；错误码分段（4xx 客户端 / 5xx 服务端 / 业务错误码表维护在 `docs/api/error_codes.md`）。
4. **核心端点基线**（沿用 P2 §8.2 并扩展）：
   - `POST /api/v1/workflow/sessions` 创建设计会话
   - `GET /api/v1/tasks/{task_id}` 查询任务状态
   - `GET /api/v1/workflow/sessions/{sid}/irs/{type}` 获取 IR（含历史版本）
   - `POST /api/v1/workflow/sessions/{sid}/reviews/gate1|gate2` 提交审阅裁决
   - `POST /api/v1/kb/documents` 上传文档 / `GET /api/v1/kb/documents` 入库进度 / `POST /api/v1/kb/build` 触发索引构建
   - `GET /api/v1/trace/{trace_id}` 溯源链查询
   - `WS /api/v1/ws/sessions/{sid}` 进度与日志推送
5. **WebSocket 消息**也必须有 schema（放 `contracts/ws/`），不允许裸字符串协议。

## 6. 知识库构建管线约束（文档预处理）

这是 v2 demo 必须做实的细节，不是"能跑就行"：

| 阶段 | 要求 |
|---|---|
| ① 入库 | 支持 PDF / Word / Excel / Markdown / TXT；上传即建档（元数据：来源、格式、上传时间、状态）；前端可见入库任务进度 |
| ② 解析 | 按格式路由解析器；扫描件走 OCR（可选插件，失败降级纯文本并标注）；解析产物保留**页码/章节位置信息**（供溯源与引用映射） |
| ③ 清洗分块 | 去噪、规整表格文本；分块策略可配置（按章节优先，重叠可调）；每个 chunk 携带 `doc_id + location` |
| ④ 结构化抽取 | LLM 按本体 Schema 抽取实体与关系（实体/关系类型按 P2 §7.2）；抽取结果人工可审（预处理阶段即提供预览，不必等图谱构建完） |
| ⑤ 索引构建 | 调用 GraphRAG 构建索引 + 写入向量库；构建为异步任务，进度可查、失败可重试（有上限） |
| ⑥ 增量更新 | 支持增量：仅处理变动文档；实体冲突与冗余要提示，不静默覆盖 |
| ⑦ 去除与回滚 | 文档删除时同步清理其 chunks/实体来源标记；图谱不支持自动删实体时，标记 `deprecated` |

**硬性要求**：知识库现状必须诚实（实体/关系数量、来源文档列表在 UI 可见）；禁止把"单案例知识库"包装成"领域知识库"。

## 7. 文档驱动开发流程（核心约束）

v2 实行**文档先行、文档与代码同步**的开发模式。规则如下：

### 7.1 文档先行

1. 任何新功能开发前，`docs/` 中必须已有对应的需求/设计说明（哪怕是 30 行的轻量设计）。没有文档的任务不开工。
2. 文档粒度分层：
   - `docs/roadmap.md` —— 阶段与任务总表（唯一进度事实源，状态：待开发/开发中/待验收/完成）
   - `docs/phase/phase-N-xxx.md` —— 阶段设计（本期范围、任务拆分、验收标准）
   - `docs/api/` —— 接口契约
   - `docs/adr/ADR-NNN-标题.md` —— 重要技术决策记录（背景/决策/后果）
   - `docs/devlog/` —— 按日开发日志（做了什么、踩了什么坑、下一步）
3. 阶段推进流程：**写阶段文档 → 拆任务并登记 roadmap → 逐任务实现 → 每任务完成即回填 roadmap 状态与 devlog → 阶段末人工验收**。

### 7.2 文档与代码同步纪律

- 每个任务完成时，**文档更新与代码改动放在同一个 commit**（roadmap 状态、devlog、受影响的 API/设计文档）。
- 禁止"代码先跑通、文档以后补"——补文档的债不允许产生。
- 与设计文档（P1/P2）发生实现偏差时，要么改实现，要么走 ADR 修订设计，不允许实现与文档长期不一致。

### 7.3 UI 变更专项约束

- 任何界面改动（新页面、布局、配色、组件）**先出 mockup/预览确认视觉方向，再落地代码**。
- 风格基线（ADR-012，2026-10-10 起）：**深色海洋科技风**——深蓝三层底（#070f1e/#0a1628/#0f2035）+ 青色交互 accent（#06b6d4，仅用于按钮/链接/选中态等可操作语义元素）；霓虹光晕、网格纹理、毛玻璃顶栏等装饰语言限定范围使用（品牌标/主按钮/进度条/运行中状态点/欢迎横幅），语义四色不用于装饰。theme.css 与 docs/mockups/mockup.css token 同源（accent 命名），改动需两侧同步。UI 不得引入假数据夸大能力（A-16 不变）。视觉基线 = docs/mockups 九页深色稿（git 05cc24f 取回）+ 用户已在真实栈确认过深色方向。
- **分层推进四条红线（v1.6 新增，违反任一即停）**：① 功能零回归——不动 api/stores/hooks/路由/数据流，风格化展示一律叠加，不删既有交互入口；② 一步一提交——build + vitest + 页面走查全绿才前进，每步可独立 revert；③ 新依赖必须单独成步，并在提交信息与会话输出显著提示 npm install；④ 每层结束跑 `docs/ui2/功能走查清单.md` 并在文末留档表登记。（历史注：ADR-011 首次深色改版因整批交付被当日回档，教训见 roadmap UI-1 小节。）

## 8. Git 与版本管理约束

### 8.1 提交纪律（小步快跑）

1. **每完成一个子任务立即 commit 并 push**，不累积提交。一个 commit 对应一个可描述的完整改动（一个任务、一个修复、一批文档）。
2. 单次 push 的 commit 数量没有硬上限，但**开发会话结束时不允许存在未提交改动**——下班前工作区必须干净。
3. Conventional Commits 格式，scope 用模块名：

```
feat(agents): A4 合规校验引擎实现等式校验
fix(pipeline): 审阅关①回退后 IR2 版本未失效
docs(roadmap): Phase-1 T3 状态回填为完成
refactor(kb): 解析器路由抽离为独立模块
api: 调整审阅关接口请求体（OpenAPI 同步更新）
chore(deps): 新增 pymupdf 用于 PDF 解析
```

4. 提交前自查：改动是否只含本任务内容；文档是否同步；`git status` 无意外文件。

### 8.2 分支与推送

- 分支模型：`main` 保持可运行；任务开发走 `feature/phaseN-task-简述` 短生命周期分支，完成后合回 `main` 并删除分支。小改动可直接在 `main` 提交。
- **push 与 commit 同步进行**（有 remote 后）；无 remote 期间本地提交照常，接入 remote 后补推。
- 禁止对 `main` 做 force push；禁止 `--no-verify` 跳过钩子。
- `.gitignore` 必须先于首个功能提交建立：排除 `.env`、`venv/`、`node_modules/`、`data/`、`output/`、`__pycache__/`、`dist/`、知识库索引产物。

### 8.3 标签与发布

- 版本号 `v0.x.y`：x = 阶段里程碑，y = 阶段内迭代。
- **打 tag 前必须走附录 A 发布检查清单**（人工测试优先，不自动部署）。
- tag 信息写清本版本包含的阶段/任务范围。

## 9. 质量与验收约束

1. **Agent 可独立运行**：每个 Agent 提供独立入口（CLI 或 pytest fixture），可脱离管线单独调试。
2. **IR 契约测试**：`contracts/ir/` 变更必须伴随契约测试更新；每个 Agent 有"合法 IR 输入 → 合法 IR 输出"的用例。
3. **端到端冒烟**：`tests/e2e/` 维护一条标准样例需求（拖曳线列阵），从需求到 STEP 全链路跑通；每次合回 `main` 前至少跑通一次。
4. **UI 验收**：mockup 确认 → 实现 → 真实样例走查（至少 2~3 组真实设计需求，覆盖正常流 + 审阅关回退流）。
5. **不做的事不假装做了**：报告与 UI 中的能力表述与实际一致（对应 A-16）。

---

## 10. 安全与配置约束

1. **密钥不入库**：API Key 只存 `.env`（已 gitignore）或本地配置；任何日志、文档、截图、提交中不得出现真实 Key。示例文档统一用 `your_api_key` 占位。
2. LLM 配置（base_url/model/api_key）存业务库并支持热切换，但 api_key 字段序列化时必须脱敏。
3. CadQuery 生成脚本只在子进程 + 独立工作目录执行，限制执行时间。
4. 上传文件大小与类型白名单校验；解析失败不中断服务。

## 11. 本文档的修订规则与违例处理

1. 修订本文任何条款（含 §2 裁剪决策表）必须：新建 `docs/adr/ADR-NNN-*.md` 说明背景与影响 → 更新本文版本表 → 同一 commit 提交。
2. 开发中发现无法满足某条硬约束（A-01~A-16）时，**立即停下记录 ADR 讨论修正**，不允许先斩后奏。
3. AI 协作开发时，每次会话开始应先读本文件与 `docs/roadmap.md`，结束时确保 roadmap/devlog 已回填、工作区已提交。
