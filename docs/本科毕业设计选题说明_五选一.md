# 本科毕业设计选题说明（五选一）

> 2026-10-30 已确定选择需求澄清方向，并扩展为知识增强对话与设计文档生成。最新下发版为一页，Pi Agent 与 GraphRAG 均为建议技术；以[单题任务说明](本科毕业设计任务说明_知识增强对话智能体.md)为准，本文件保留为选题历史，不再作为当前任务书。

编制日期：2026-10-30。适用安排：一名本科生，从以下五题中选择一题，建议周期 12 周。

## 一、共同背景与工作方式

工程设计及技术资料管理常遇到需求不完整、资料难检索、知识重复、生成建议缺少依据、不同版本资料相互矛盾等问题。以下课题分别研究其中一个通用问题，并实现可演示的独立系统。

每题均在独立仓库、独立环境中完成。只需了解上述背景，自行设计数据结构、接口、前后端与实验，不需要了解或修改已有项目，不需要访问其数据库、代码或运行服务。后续由项目维护者参考研究方法、实现代码与实验结论，自行决定如何改造已有项目；本次毕业设计不承担集成、兼容或即插即用要求。

共同成果为：明确的研究问题、可比较基线、一个核心改进、可操作前端、实验与误差分析、独立源码及启动说明。算法不一定优于基线，但结论必须有证据；能否满足毕业要求由导师按学校要求确认。

## 三、题目 1：清单驱动的多轮需求澄清方法研究与系统实现

### 1. 要解决的问题

用户一次性描述设计需求时，可能遗漏用途、规模、环境、约束和验收条件。普通聊天虽然能继续提问，但容易重复、遗漏重点或擅自补充信息。本题研究如何依据一份可配置需求清单，有限轮次地补齐信息，生成由用户确认的需求说明。

### 2. 功能需求与前端

1. 输入初始需求，选择需求清单，例如通用设备选型或软件功能需求场景。
2. 显示已知、缺失、存在矛盾及用户明确暂不确定的信息。
3. 每轮提出少量有针对性的澄清问题，允许修改回答、跳过和结束。
4. 生成需求草稿，并能追溯到原始输入或某轮回答；用户确认后导出文本/JSON。
5. 前端包含聊天区、澄清卡片、完整性侧栏、草稿预览和策略对照页。

### 3. 大概技术路线

建议 Python + FastAPI + React（或学生熟悉的其他前端）+ SQLite；语言模型通过可配置 API 调用，不要求训练模型。清单存为自行定义的 JSON/YAML，后端用“收集—澄清—确认”状态控制交互。

基线为固定顺序清单提问和自由问答；核心改进可用缺失项优先级、冲突优先及重复问题抑制来选择下一轮追问。只需研究一种改进策略，不叠加复杂自主智能体。

### 4. 数据与实验

选择一个范围明确的通用场景，整理完整需求及其遗漏/歧义版本，预先确定评分清单。比较需求完整率、矛盾率、无依据新增信息率、交互轮次和调用成本；相同场景、相同交互预算下做配对比较。模型模拟用户与真实人员试用应分别报告，不能当作同一种证据。

### 5. 范围、兜底与成果

首版只支持一种场景、有限轮次与文本成稿；流式输出、语音、长期记忆不必做。模型不可用时保留清单式收集，能运行基线。交付独立网站、策略模块、清单/场景数据、实验报告和运行说明。

## 四、题目 2：面向技术文档的混合检索方法研究与可视化评测系统

### 1. 要解决的问题

技术资料中，精确术语适合关键词匹配，而近义改写更依赖语义检索。不同检索方法效果和响应开销不同。本题研究组合检索及重排序在不同查询类型下的收益和代价，并提供可交互评测工具。

### 2. 功能需求与前端

1. 导入一组公开技术资料，完成分块、元数据管理与本地索引；首版可只支持 TXT/Markdown。
2. 同一查询分别执行关键词检索、向量检索和融合检索，显示原文片段与排序。
3. 维护带相关性标注的查询集，支持标注、批量实验和导出结果。
4. 配置融合参数、返回条数和是否重排，保存实验配置。
5. 前端包含同查询多列结果对照、来源预览、相关性标注页和指标/耗时看板；不同方法分数注明含义，不直接当同一量纲比较。

### 3. 大概技术路线

建议 Python + FastAPI + React，BM25 作为关键词方法；embedding 使用本地可运行模型或可配置 API，向量检索采用 NumPy/FAISS 等独立索引即可。用 RRF 融合候选排序，可选增加交叉编码器重排序。

先做 BM25、稠密向量、RRF 三组，再比较 RRF+重排；融合参数选择只使用调试集。不要求部署大型向量数据库或训练新模型，也不同时研究答案生成。

### 4. 数据与实验

选择一个公开、范围明确的技术文档集合。先用约 30–50 条人工核验查询做先导实验，再与导师确定正式测试量与标注规则；按术语查询、语义改写、多条件等类型分析。同一意图的改写放在同一组划分，避免调试/测试泄漏。

评价 Recall@k、MRR、nDCG@k、响应时间与成本，报告逐查询差异、参数敏感性和失败案例。若融合无提升，分析语料规模、查询类型和候选召回原因。

### 5. 范围、兜底与成果

首版只做文本块检索，PDF/OCR、图谱融合、自动问答均后置。API 不可用时仍应能运行 BM25 与固定本地评测。交付独立评测网站、排序模块、语料/查询标注说明、实验配置及原始结果。

## 五、题目 3：融合名称与邻域特征的知识图谱重复实体识别方法研究与系统实现

### 1. 要解决的问题

由多份资料构建的知识图谱可能出现别名、缩写、重复实体，也可能存在“同名但不同对象”。本题研究如何结合名称、类型和邻域关系发现重复候选，并通过人工确认避免误合并。

### 2. 功能需求与前端

1. 导入自定义节点/关系 JSON 或 CSV，展示实体与局部关系；不要求运行现有业务图库。
2. 生成疑似重复实体对，显示名称、类型、共同邻居及相似度依据。
3. 允许标记重复/不重复/待确认，并记录标注。
4. 预览合并后的属性、关系及冲突，由人工确认后在独立数据副本中执行，支持撤销。
5. 前端包含候选列表、实体并排对照、局部图、合并前后对照及检测指标面板。

### 3. 大概技术路线

建议 Python + NetworkX + SQLite + FastAPI，前端使用 React + D3/ECharts 等图可视化库；Neo4j 为可选项。先按实体类型或名称特征筛选候选，再计算字符串相似度、类型一致性和邻域集合相似度，组合为重复得分。

基线为名称相似度，逐步增加类型与邻域特征做消融。合并阶段用明确规则处理同属性冲突、重复关系与自环，保存变更前数据以便撤销。

### 4. 数据与实验

可从公开实体关系数据构造一个规模适中的图，人工标注重复对与同名非重复难例；真实重复不足时受控注入别名/缩写/重复关系，真实集和注入集分别报告。划分时尽量按实体组隔离，防止同一实体的别名跨调试和测试。

评价候选召回、最终重复对 Precision/Recall/F1、错误合并率、候选数量与耗时。节点减少或图更连通不能单独作为质量提升证据。

### 5. 范围、兜底与成果

只做一种图模式、重复检测与可逆合并；不做全功能图编辑平台或自动大规模合并。邻域信号不足时保留名称/类型基线及人工确认。交付独立网站、检测与合并模块、图数据及标注说明、消融实验和撤销演示。

## 六、题目 4：基于结构化证据约束的大模型建议生成方法研究与系统实现

### 1. 要解决的问题

语言模型提出建议时，可能编造数值、引用无关材料或把一个对象的信息用于另一个对象。本题研究如何让建议绑定明确证据，并检查“证据是否真的支持这条建议”。

### 2. 功能需求与前端

1. 输入问题描述、对象/参数信息及若干证据片段，证据包含编号和出处。
2. 生成建议卡片，每条显示行动方向、适用对象、引用证据和证据不足提示。
3. 校验证据编号、对象、参数、单位及数值关系；将结构校验和语义支持核验分开显示。
4. 点击建议时高亮对应原文，支持人工标记支持/不支持/不确定，并导出建议报告。
5. 提供批量对比实验页，展示无约束与不同约束方法的输出和指标。

### 3. 大概技术路线

建议 Python + FastAPI + React + SQLite + 可配置 LLM API。先设计独立的“问题—事实—证据—建议”数据结构，通过 JSON 结构化输出生成建议，再做引用存在性、对象/单位/数值一致性检查。

对比无约束生成、数字集合过滤、对象—参数—证据绑定三组。数字出现过、证据 ID 存在都不能单独证明语义忠实；采用人工标注核验，并可将模型判别作为辅助研究项。

### 4. 数据与实验

选取通用技术检查或参数核对场景，整理有支持、证据不足、冲突、错对象和单位换算等样例。先建立人工判定规则，再构造与标注案例；划分时按问题/证据场景分组。公开资料、真实整理案例和人工注入反例分别说明。

评价声明级支持率、无依据数值率、错误对象引用率、有效建议覆盖率、拒答率与成本，避免仅靠全部拒答提高忠实率。相同上下文比较不同方法，并分析拒答与有效建议之间的权衡。

### 5. 范围、兜底与成果

只生成与解释建议，不执行修改、不代替人工裁决；公式新值由明确的确定性计算给出或不提供。证据不足时拒答，模型故障时可显示来源明确的模板建议并标明模式。交付独立网站、建议生成/校验模块、标注数据与实验报告。

## 七、题目 5：面向多版本工程文档的依赖一致性检测方法研究与可视化系统

### 1. 要解决的问题

一项方案可能同时包含需求、参数表、模型说明和检查报告。上游更新后，下游可能仍引用旧版本，或把不同版本材料混在一起。本题研究如何依据显式依赖识别这些问题，并解释变更影响。

### 2. 功能需求与前端

1. 导入独立设计的版本清单：文档/数据项 ID、版本、时间、状态及引用的上游版本。
2. 展示时间线和依赖图，查看同一对象的版本差异。
3. 检测过期引用、缺失依赖、无效上游及不一致的版本组合，并给出原因路径。
4. 用户模拟更新或撤回某个版本，观察哪些材料可能需要重做；不自动修改原始文档。
5. 输出可阅读诊断报告和结构化结果，支持批量场景评测。

### 3. 大概技术路线

建议 Python + NetworkX + SQLite + FastAPI，前端 React + 图/时间线组件。首版处理明确 JSON/CSV 版本清单，不要求从任意 Word/PDF 中自动抽取依赖。

基线为只比较版本是否最新；改进方法建立有向依赖图，通过遍历和状态规则检测错配、传播影响，并输出解释路径。明确允许固定引用旧版的情形，不能把“不是最新”一律判错；缺依赖信息输出未知。依赖环、缺失节点等先作输入合法性检查。

### 4. 数据与实验

围绕“需求—参数—模型说明—报告”等通用流程构造正常与变更场景，标注应报问题及正确影响集合。加入旧版合法引用、版本号不同但无依赖、链式失效、分支更新与缺失信息等反例；构造规则与真值生成过程可复查。

按流程模板分组划分调试/测试，避免只在同一模板改几个版本号。比较错配检测 Precision/Recall/F1、影响集合 Precision/Recall、误报率和耗时；去掉依赖或状态规则做消融。受控场景结论不能冒充真实生产效果。

### 5. 范围、兜底与成果

范围限离线诊断与可视分析，不做协同审批、权限系统或发布控制。无复杂算法条件时保留规则基线，通过反例、消融和解释质量分析形成研究。交付独立网站、检测模块、版本场景集/真值、实验与解释报告。

## 八、共同周期与交付要求

| 周次 | 必须完成的内容 |
|---|---|
| 1–2 | 读相关方法，选定一个场景；确定数据来源、基线、评价指标；跑通样例并提交 UI 草图 |
| 3–4 | 基线可运行，最小前端可操作；做先导实验，和导师确认正式范围 |
| 5–7 | 完成一个核心改进、消融方案、必要标注及主要界面 |
| 8–9 | 冻结测试数据与配置，开展正式实验，保存原始结果和失败案例 |
| 10–12 | 完成误差分析、论文、独立部署与演示；整理源码、数据说明和复现步骤 |

每题均交：独立源码仓库、前后端运行说明、依赖清单、示例数据与来源/标注说明、原型输入输出说明、基线与改进实验脚本、配置与原始结果、论文及演示材料。自己的接口需清楚、可测试，但不需要符合任何已有项目的数据格式。

技术栈为建议，可与导师商定后采用更熟悉的工具；优先使用简单本地存储，不为了技术堆叠部署完整微服务。数据集、标注量、模型可用性与调用预算在第 2 周前确认；未落实时先使用公开或受控小样例验证，及时收缩范围。涉及数据、模型或第三方代码时如实注明来源与许可。

如模型 API 不可用，可用固定回放展示交互，但必须标明回放模式，正式实验仍需保留真实运行记录；UI 不能把预置结果当实时模型能力。模型返回内容可能变化，记录模型标识、提示词、配置和时间；确定性方法与随机模型分别说明复现方式。
